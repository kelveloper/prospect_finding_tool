Talking points: what we can actually use

The manager asked for conversation starters an advisor can open with. This is what exists, what it costs, what it is allowed to do — and the single rule that decides all of it.

The short version

Five things — enough to answer anyone who asks

  1. DuckDuckGo cannot be used, and it is not a licensing problem. It has no API for applications, because it does not own its search results — it licenses them from Bing. There is nothing to buy and nothing to connect to.
  2. We found a better free source: CMS Open Payments. It records what drug and device companies pay each physician. It matches on NPI number, so there is no risk of pulling the wrong person. Measured on our real data: 24 of 40 prospects have a record, and 9 of 40 have something worth opening a conversation with.
  3. The rule that decides everything: match on an ID number, never on a name. Every wrong match we found came from name matching — including an MIT physicist and a supermarket director in North Carolina, both returned for physicians in our book.
  4. Buying data does not solve this. Across about 35 vendors, the ones that can find physicians carry no wealth information, and the ones with wealth information cannot find physicians. Nothing sells both. Our free public-records approach is the better design, not the cheap option.
  5. The tool must hand advisors facts and links, never a written-out message. If software writes the wording and it goes to many prospects, SEC rules treat it as an advertisement, with approval and archiving obligations attached.

If someone asks you

Short answers, in plain words

"Why can't we just use Google or DuckDuckGo?"
DuckDuckGo has no API at all. Google's version is closing to new customers and shuts down in January 2027. The services that scrape Google for you are being sued by Google right now.
"Why not just search the doctor's name?"
Because names are not unique and we would tell an advisor something false. Searching one of our orthopedic surgeons returned an MRI physicist at MIT. Searching another returned a company director in North Carolina. We only use sources that match on an ID number.
"Can't we just buy this from a vendor?"
We checked about 35. The healthcare ones cost $25,000 to $500,000 a year and only tell us who is a doctor — which we already know for free. The wealth ones cannot identify physicians at all. Also, no financial advisor firm we could find actually uses one; they use referrals.
"Is it legal for us to use this data?"
Yes. US government data is public domain — free for internal and commercial use, no licence needed. It is the same legal footing as the four sources we already use.
"Why not let AI write the opening message?"
Because software-written outreach sent to many people counts as an advertisement under SEC rules, which brings approval and record-keeping requirements. We give the advisor the facts and the source link, and they write their own note.
"What about personal details — family, kids, their house?"
We deliberately do not. It reads as surveillance rather than preparation, and it is the category regulators treat as sensitive. Our own contact kit already hides the property purchase for the same reason. A professional opener works better anyway.
"If we can download the government data, why can't we download DuckDuckGo?"
Because CMS publishes an actual file of records and DuckDuckGo has no file to publish. It looks things up live in Bing's index and shows you the answer — nothing is stored to hand over. You can download the book; you cannot download the librarian.
"What would this cost?"
Nothing for the recommended sources. If we later wanted live web search inside the tool, it would be roughly two dollars a month at our size.

1. The original question

What the manager suggested, and why it does not exist.

The suggestion was DuckDuckGo — search the prospect online and use whatever comes back. The concern raised was whether it would be licensed for our internal use.

That concern turned out to be the wrong one. DuckDuckGo has no web-search API at all. It has exactly one official API, Instant Answers, and it returns nothing for ordinary people:

Measured — DuckDuckGo Instant Answer API

Sepideh Amin-Hanjani → 0 results
Ali Alaraj → 0 results
Jeffrey Ackerman → 0 results

The endpoints the Python DuckDuckGo libraries scrape (html.duckduckgo.com, lite.duckduckgo.com) both returned HTTP 202 — an anti-bot soft block, not results. That is why those libraries break every few months.

So the answer to bring back is: not available, but not for licensing reasons. DuckDuckGo simply does not sell or expose search results to applications. The instinct was fine; the plumbing does not exist.

Why there is no API — DuckDuckGo does not own its results

This is the part that makes the rest make sense. DuckDuckGo is mostly a metasearch engine. It does not run a large index of the web. When you search, it is largely passing through results licensed from Bing, mixed with Wikipedia and Wikidata for the instant answers and its own small crawler for some pages.

So there is no API not because they never built one, but because the results are not theirs to resell. Their licence from Microsoft does not grant redistribution. You cannot buy from DuckDuckGo something DuckDuckGo does not own.

Could we scrape it instead?

We tested this properly — a request dressed as a real Chrome browser, full user-agent, hitting the same endpoint the Python DuckDuckGo libraries use:

Measured — scraping attempt with a browser user-agent

HTTP 202  |  14,250 bytes downloaded
results parsed out of the HTML: 0
page content: the word "DuckDuckGo", and nothing else

An empty shell page. The block is server-side, so disguising the request does not help. Getting past it would mean rotating proxies and solving challenges — a terms violation, and legally live right now: Google's lawsuit against SerpApi over exactly this is unresolved. Not something to put inside a regulated firm's tool.

And no, a search index cannot be downloaded

A reasonable next thought is: could we just download the search results in bulk and query them locally? Not for a search engine. Google's and Bing's indexes are their entire business and are not distributed. The closest free thing is Common Crawl, which genuinely is a downloadable archive of the web — but we tested it, and it has no ranking and no search-by-person. You must already know the URL you want. It is raw material for building a search engine, not a search engine.

The distinction that matters — and the one people get wrong

CMS Open Payments is a dataset. A finite list of rows about physicians, which CMS publishes as a file on purpose, for anyone to take. That is why we can download it and query it locally forever.

DuckDuckGo is not a dataset. There is no file of "all DuckDuckGo results" anywhere, not even inside DuckDuckGo. You type a question, it asks Bing, it shows you what comes back. There is nothing stored to hand over.

Put another way: CMS is a library that will mail you a copy of the book. DuckDuckGo is a librarian who looks things up in someone else's library and reads the answer out to you. You can download the book. You cannot download the librarian.

2. The one rule that decides everything

This is the part worth understanding. Everything else follows from it.

A data source is only usable if we can be certain the record belongs to our physician. There are two ways to make that link:

  • Join on an identifier — an NPI number, an ORCID iD. These are unique to one person. A match is a fact.
  • Join on a name — "Jeffrey Ackerman". These are not unique. A match is a guess.

The codebase already has the correct rule for this, in EnrichmentMatcher: attach or drop, never fuzzy match. A miss is acceptable; a false match is not. The research produced a pile of evidence for exactly why.

Every single false positive found across all five research passes came from a name join. Not one came from an identifier join.

  • Ackerman J + Chicago/orthopaedic affiliation PubMed

    Returned Jerome L. Ackerman, an MIT MRI physicist. Affiliation filters do not fix this — they match any co-author's affiliation on the paper, not the target author's.

  • Jeffrey Ackerman, insider forms SEC EDGAR

    Returned a director of Fresh Market Inc. in North Carolina. Different person, different state, different profession.

  • Ahmed Mohammed[Author] PubMed

    Returned 1,170 papers spanning many different physicians with the same name.

  • Amin-Hanjani NIH RePORTER

    Top-ranked hits were DE HAVENON and ZIPFEL — unrelated researchers. The API's own relevance ranking cannot be trusted without an exact-match post-filter.

This is why the recommendation below is not simply "the sources with the most data". It is "the sources we can attach without lying to an advisor".

Open Payments is the strongest because it joins on NPI, exactly like PECOS already does — zero misattribution risk. ClinicalTrials.gov earns its place despite being name-based because it returns the investigator's affiliation, which we can check against the PECOS group name we already store. That converts a guess into a verified match.

Tier 2 — cheap additions

  • NIH RePORTER — free, but must post-filter principal_investigators[] for an exact match, per the failure above.
  • FEC contributions — not a talking point. Political donations make a bad opener. But it returned ACKERMAN, JEFFREY | IBJI | PHYSICIAN | Glencoe IL — employer and occupation, which is a free correctness check on our NPPES data.
  • A research-links row in the contact kit — pre-built links that open DuckDuckGo, the practice website and PubMed in the advisor's own browser. Zero cost, zero terms risk, and it is exactly what the manager does by hand today.

Tier 3 — park, do not discard

  • IRS Form 990 board seats. The best talking point of anything tested — shared philanthropic interest is both flattering and appropriate. But ProPublica's API does not expose officer names (measured: 0 hits on person queries) and the free bulk mirror froze in December 2021. Officer names exist only inside raw 990 XML, Part VII. That is a data-engineering project, not a sprint task.
  • A paid search API, only if in-tool results are required. At our volume this is genuinely cheap — roughly $2 a month for 219 prospects at $10/1,000 queries.

Download once, query locally — for the government data, not for search

The government sources are built to be downloaded, and Open Payments publishes the whole year as a single CSV. Confirmed live:

OP_DTL_GNRL_PGYR2024_P06302026_06032026.csv → HTTP 200

So instead of calling the API once per prospect, we download the file once, filter it to our NPIs while streaming, and write the matches into SQLite. Four reasons that is better than the API:

  • One download instead of 219 calls — and it covers every future prospect too, not just today's list.
  • No rate limits and no per-query cost.
  • Reproducible. The filename carries its publication date, so the audit trail can cite the exact file version behind any claim — which is precisely what the Marketing Rule's substantiation requirement asks for.
  • It works offline. The demo stops depending on a live API responding.

The catch is size: the full-year file is millions of rows. Stream and filter during download, keep only matching rows, and we store a few thousand rows rather than the whole country.

4. What the advisor actually sees

Real records from our own book, pulled live. This is the part that was missing.

First, a common misreading. Open Payments is not what a physician prescribes. It is money flowing from drug and device companies to the physician — consulting fees, research grants, teaching, royalties, travel, meals. Prescribing is an entirely separate dataset we do not use.

Which category the payment falls into is what decides whether it is worth anything:

Note what the panel does not do. It does not write the advisor's opening line. It gives them a fact, the source behind it, and why it is financially relevant. The advisor decides what to say — which is what keeps this out of advertisement territory under the Marketing Rule (section 6).

What a human might do with that, in their own words: "I saw you've been consulting on the neurovascular side with J&J — is that a growing part of your practice?" That sentence is the advisor's to write, not ours to generate.

The finding worth telling the manager

Across roughly 35 vendors, searching Kitces, XYPN, Bogleheads, r/CFP and White Coat Investor, there was no practitioner evidence that any physician-focused RIA uses a paid prospecting platform. XYPN's own benchmarking shows the real lead sources are referrals, organic search and networking.

There is no vendor that does what we want. The NPI-joinable ones have no money data; the money ones cannot find our physicians. Our free public-records stack is the better architecture — not a budget compromise.

6. The compliance constraint that shapes the build

One finding here changes the design directly.

Generated prose would make our outreach a regulated advertisement

The SEC Marketing Rule adopting release (IA-5653) states:

"Customizing a template presentation or mass mailing by filling in the name of an investor and/or including other basic information about the investor would not result in a one-on-one communication."

So the one-on-one exclusion does not protect us once the tool writes the language. Machine-templated outreach sent to many prospects is an advertisement — triggering substantiation, fair-and-balanced and archiving obligations.

The design conclusion: give the advisor sourced facts and links, never drafted prose. outreach/service.py already says "No drafted correspondence — the advisor writes their own outreach." That instinct turns out to be a compliance asset, not just good taste.

The rest, briefly

  • We are almost certainly not a "data broker" under California, Texas, Oregon, Vermont or the pending Illinois bills. Every one of those definitions requires selling or licensing to third parties. Internal-only use does not qualify — but it flips the moment we share prospect data with a referral partner or license the tool to another firm. Worth a hard block in code.
  • Reg S-P does not cover pure prospects, only people who actually engage. Our pipeline sits outside it. It is a named 2026 exam priority, so this is worth stating precisely rather than assuming.
  • FCRA — marketing is not a permissible purpose, and a vendor's "not a consumer report" disclaimer does not control the analysis. Reinforces skipping the people-search tier entirely.
  • No enforcement precedent was found on advisors referencing personal details in solicitation. Genuinely unresolved rather than settled. The nearest standard is the FTC's treatment of sensitive inferences drawn from ordinary data — which does cover life events inferred from property records.

Guardrails to build in

  • Facts and links, never generated prose.
  • A provenance ledger — every claim traces to a source record and date, so substantiation is answerable.
  • A hard block on exporting prospect data outside the firm.
  • The CMS disclaimer wherever Open Payments data surfaces: a payment record does not indicate an improper relationship.

7. Two things this changed about our own data

Found incidentally, both worth acting on.

  • Avinesh Agarwalla has moved to Cedars-Sinai in California. He is still ranked in our Illinois book. This is another instance of KNOWN_GAPS.md §1, and it suggests OpenAlex could double as a staleness check on practice location.
  • Community physicians return nothing, correctly. Jeffrey Ackerman has no scholarly footprint, and every source correctly declined to invent one. That is the right behaviour — but it means this layer only ever covers academically active prospects, and the board should not imply otherwise.

8. Open questions
